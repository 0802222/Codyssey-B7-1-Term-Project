## 1. 서비스 이해

### 우리 서비스는 어떤 문제를 해결하나? ✅
처음 배우는 사람에게 개념 설명은 **너무 어렵거나 너무 얕아서** 다시 찾아봐야 하는 일이 많습니다.
EasyExplain 은 같은 개념을 **아주 쉽게 / 입문자 / 전공자** 수준으로 골라 설명받고, "더 쉽게", "예시 하나 더", "핵심만" 으로 이어서 물어 이해를 넓히게 합니다.
근거: README 1장, `app/chat/prompts.py`(수준별 지침)

### 사용자는 어떤 가치를 얻나? ✅
- 내 수준에 맞는 설명을 **한 대화 안에서** 바꿔 가며 받음 (문맥 유지, 수준 변경)
- 대화가 저장돼 **내 기록에서 다시 보고 이어서 질문** 가능
- 키보드·휴대폰으로도 사용 (접근성 #56)

근거: `/chat`, `/history` 화면, [EE-19 실제 답변 샘플](../../app/chat/EE-19.md)

## 3. 확장성

### 사용자 증가를 감당할 수 있나? 한계 지점과 확장 방법 🟨
**지금 구조는 평가 규모(수십 명)용입니다.** 한계가 오는 지점과 바꿀 구조를 알고 있습니다.

| 한계 지점 | 왜 | 바꿀 구조 |
|---|---|---|
| SQLite 쓰기 | 한 번에 하나만 씀. 동시 질문이 많아지면 대기 | PostgreSQL |
| 서버 1대 (Replica 1) | Volume 은 서버 하나만 붙음. 배포 중 1~2분 중단 | DB 를 별도 서버로 → 서버 여러 대 + 무중단 배포 |
| 질문 횟수 제한·처리 중 표시 | 서버 메모리에 있어 서버가 여러 대면 정확하지 않음 | Redis 같은 공유 저장소 |
| AI 응답 대기 (최대 30초) | 요청이 오래 붙잡힘 | 작업 큐 + 결과를 나중에 받는 방식(폴링·스트리밍) |
| 채팅 API 안의 동기 DB 호출 | `async` 함수 안에서 DB 를 동기로 불러 그 순간 이벤트 루프가 멈춤 (8장) | 비동기 DB 드라이버, 또는 DB 부분을 스레드로 |

근거: `app/chat/EE-16.md`(단일 worker 전제), 배포 문서 8장 Replicas 1

### 캐시 정책이 적절한가? 🟨
- **API**: 화면의 조회 요청은 `cache: "no-store"` 로 보내 오래된 기록을 보지 않음 (`app/static/js/api.js`) ✅
- **HTML 페이지**: 캐시 헤더 없음 → 매번 서버에서 새로 받음
- **정적 파일(CSS·JS)**: `ETag`·`Last-Modified` 는 있지만 `Cache-Control` 을 **따로 정하지 않았음.** 브라우저가 스스로 판단해 잠시 캐시할 수 있음

### 배포 후 예전 캐시 페이지를 보고 있다면 어떻게 무효화하나? ❌ (방법은 앎)
지금은 정적 파일 주소가 배포마다 같아서(`/static/js/chat.js`), 브라우저가 예전 JS 를 잠시 쓸 수 있습니다. 바꿀 방법:
1. **주소에 버전 붙이기**: 템플릿에서 `/static/js/chat.js?v=<배포 커밋>` → 배포하면 주소가 바뀌어 새로 받음 (가장 확실)
2. 정적 파일에 `Cache-Control: no-cache` → 매번 `ETag` 로 확인하고 바뀌지 않았으면 304
3. 이미 열린 페이지는 API 오류 형식이 그대로라 동작은 하고, 새로고침하면 새 파일을 받음

## 4. 외부 서비스(AI API) 의존성

### AI 에 장애가 나면 우리 서비스는? ✅
서버는 멈추지 않고, 그 질문만 실패로 저장하고 안내합니다. 다른 기능(로그인·기록)은 그대로 동작합니다.
근거: `app/chat/service.py`, 배포 서버 시간 초과 재현 ([EE-23](../../app/chat/EE-23.md)), `tests/integration/test_failure_paths.py`

### `429 Too Many Requests` 가 오면? ✅
두 가지를 구분합니다.
- **AI 게이트웨이가 429**: `401/403/404/429` 를 `AIUnavailableError` 로 바꿔 사용자에게 503 `AI_UNAVAILABLE` "지금은 AI 를 이용할 수 없어요" (`app/chat/anthropic_provider.py`)
- **우리 서비스의 한도 초과**(사용자 1분 10회, 전체 하루 200회): AI 를 부르기 전에 429 `RATE_LIMITED`. 화면은 10초(연속이면 최대 60초) 보내기를 잠그고 남은 시간 표시

근거: `app/chat/rate_limit.py`, `tests/chat/test_chat_limits.py`, `app/static/js/chat.js`

### 응답이 없으면 얼마나 기다리나? ✅
**30초**(`AI_TIMEOUT_SECONDS`). SDK 시간 제한과 별도로 `asyncio.timeout` 으로 연결부터 응답까지 전체를 제한합니다. 넘으면 504 `AI_TIMEOUT`.
근거: 배포 서버에서 1초로 바꿔 실제 504·failed 저장·서버 유지·복구를 확인 (EE-23)

### Timeout · Retry · Fallback 정책 🟨
| 정책 | 지금 | 이유 |
|---|---|---|
| Timeout | 30초 | 사용자가 기다릴 수 있는 한계 |
| Retry (자동) | **안 함** (`max_retries=0`) | 같은 질문으로 비용이 두 번 나가고 대기가 길어짐 |
| Retry (사용자) | 오류 칸의 [다시 보내기]. 같은 요청 번호면 서버가 AI 를 다시 부르지 않고 저장된 결과를 돌려줌 | 중복 처리 방지 (idempotency) |
| Fallback | **없음** — 다른 모델·고정 답변으로 대신하지 않음 | 틀린 답을 주는 것보다 "지금은 안 된다" 가 학습 서비스에 안전 |

### 다른 AI 서비스로 쉽게 바꿀 수 있나? ✅
AI 호출은 `AIProvider` 경계(`generate_reply(messages, system, ...) -> AIResult`) 뒤에 있습니다.
새 서비스용 클래스 하나를 만들고 `get_ai_provider` 의 설정 분기만 추가하면 채팅 서비스 코드는 바뀌지 않습니다. 가짜 AI 도 같은 경계로 끼웁니다.
근거: `app/chat/provider.py`, `app/chat/fake_provider.py`

## 5. 장애 대응 및 로깅

### 로그로 원인을 찾고 복구할 수 있나? ✅
요청마다 서버가 `request_id` 를 발급해 모든 로그에 붙이고, 오류 응답 본문에도 같은 ID 를 넣습니다. 사용자가 본 오류 → ID → Railway Logs 검색으로 요청 → AI → DB 저장 흐름을 바로 찾습니다.
실제로 배포 장애 2건(가입 403, 배포 Crashed)을 로그와 재현으로 찾아 고쳤습니다. → [트러블슈팅 4·5번](4-troubleshooting.md)

### 로그는 어디에, 어떤 형식으로? 🟨
- **어디:** 표준 출력 → **Railway Logs** (대시보드에서 검색). 따로 파일·외부 로그 서비스에 보관하지 않음. 보관 기간은 Railway 요금제를 따름(미확인)
- **형식:** 한 줄 `시각 수준 이벤트 request_id=… key=value` — 사람이 읽기 쉽고 ID 로 검색하기 쉬움 (JSON 구조 로그는 아님)

```
2026-10-10 15:46:40,703 INFO ai_call_start request_id=f5a2… user_id=4 turn_id=18
```

근거: `app/core/logging.py`, `app/core/middleware.py`

### 어떤 수준의 로그를 남기나? ✅
| 수준 | 언제 | 예 |
|---|---|---|
| INFO | 정상 흐름 | `request_received`, `ai_call_start`, `db_save_success` |
| WARNING | 예상한 실패 | `ai_call_failed error_code=AI_TIMEOUT` |
| ERROR | 예상 못 한 오류·DB 실패 | `db_save_failed error_type=OperationalError`, 500 |

**남기지 않는 것:** 비밀번호, 쿠키, 토큰, API 키, 질문·답변 원문, 예외 메시지 원문. 통합 테스트가 로그 전체에 이 값들이 없는지 검사합니다 (`tests/integration/test_request_logs.py`).

### DB·서버 장애가 나면? 원인, 감지, 복구 🟨
| 상황 | 서비스 동작 | 근거 |
|---|---|---|
| DB 읽기·쓰기 실패 | 롤백하고 503 `DB_ERROR` 안내, 성공으로 위장하지 않음, 서버 유지 | `tests/integration/test_failure_paths.py` |
| 처리 중 서버 재시작 | 다음 시작 때 남은 `pending` 질문을 `interrupted` 로 정리, AI 를 자동으로 다시 부르지 않음 | `app/db/session.py`, #48 |
| 잘못된 설정으로 배포 | 운영에서 가짜 AI·키 없음·쿠키 보안 꺼짐이면 일부러 시작하지 않음 | `app/core/config.py` |

- **주요 원인:** 디스크(Volume) 가득 참, 잘못된 환경 변수, 동시 쓰기로 인한 DB 잠금, 배포 중 재시작
- **감지:** `/health` 가 DB 연결까지 확인(`{"db":"ok"}`), Railway 가 배포 때 `/health` 로 확인. **알림(모니터링)은 없음** — 팀원이 사이트·로그를 보고 알아챔 ❌
- **복구:** 설정 수정 후 재배포 또는 이전 배포로 Rollback. DB 는 SQLite `backup()` 으로 파일 백업 → 내려받기 (Railway Volume 백업은 Pro 요금제 필요). 2026-10-11 백업 → 복사본으로 서버 기동까지 리허설함

## 6. 인증 및 보안

### 인증과 인가 ✅
- **인증(누구인가):** 로그인하면 무작위 토큰을 **HttpOnly 쿠키**로 주고, DB 에는 토큰의 **해시와 만료 시각**만 저장. 요청마다 쿠키 → 해시 → DB 조회로 사용자를 찾음
- **인가(무엇을 할 수 있나):** 모든 조회에 **로그인 사용자 ID 를 조건으로** 걸어 남의 대화는 없는 대화와 똑같이 404. 상태를 바꾸는 요청은 CSRF 토큰과 Origin 까지 확인

근거: `app/auth/dependencies.py`, `app/conversations/repository.py`, `tests/integration/test_failure_paths.py`

### 같은 사용자가 여러 기기에서 동시에 접속하면? ✅
로그인할 때마다 **기기별로 세션이 따로** 만들어져 동시에 쓸 수 있습니다. 한 기기에서 로그아웃하면 **그 기기 세션만** 끝납니다.
동시에 질문하면 같은 사용자의 질문은 한 번에 하나만 처리하고 나머지는 409 `CHAT_BUSY` 로 안내합니다 (AI 중복 호출 방지).
"모든 기기에서 로그아웃"·동시 접속 수 제한은 만들지 않았습니다.

### 악의적인 입력은? ✅
| 공격·입력 | 막는 방법 |
|---|---|
| 형식이 틀린 요청, 약속에 없는 필드(`user_id` 끼워 넣기) | 요청 형식 검증 → 422, 사용자는 항상 서버 인증으로 결정 |
| 빈 질문, 2,000자 초과 | 서버 검증 + 화면 제한 |
| `<script>` 가 섞인 답변·질문 (XSS) | 화면은 `textContent` 로만 표시 |
| 다른 사이트에서 몰래 보내는 요청 (CSRF) | 로그인·가입은 Origin 확인, 나머지는 CSRF 토큰 (한글 토큰도 403, #40) |
| SQL 삽입 | SQLModel 이 값을 매개변수로 넘김, 문자열로 SQL 을 만들지 않음 |
| 무차별 요청 | 질문 횟수 제한 429 |
| 아주 큰 페이지 번호 | `offset` 상한 422 (#57) |

### 쿠키가 위변조되면? ✅
세션 쿠키는 서명된 값이 아니라 **추측할 수 없는 무작위 값**(32바이트)입니다. 서버는 쿠키를 해시해서 DB 에서 찾기 때문에, 한 글자만 바꿔도 일치하는 세션이 없어 401 이 됩니다. 만료된 세션도 401.
DB 에는 해시만 있어서 DB 가 유출돼도 쿠키를 만들 수 없습니다. 쿠키는 `HttpOnly`(스크립트 접근 차단), `Secure`(HTTPS 만), `SameSite=Lax`.

## 7. 사용자 경험 및 예외 처리

### 응답이 길어지면 진행 상태 안내 ✅
보내기 버튼이 "기다리는 중…" 으로 잠기고 "답변을 만드는 중" 표시, 입력칸은 읽기 전용. 30초가 넘으면 시간 초과 안내.
근거: `app/static/js/chat.js`, #47

### 오류가 나면 무엇을 보여 주나 ✅
서버의 한국어 안내(`error.message`)를 오류 칸에 표시하고, 내부 코드·예외 내용은 보여 주지 않음. 입력한 질문은 지우지 않음. 기록 화면은 실패한 질문을 원인별 안내("응답이 늦어져 답을 받지 못했어요", "질문 한도에 걸려 답을 받지 못했어요" 등)로 보여 줌.

### 네트워크가 느리거나 끊기면 ✅
서버에 닿지 못하면 "서버에 연결하지 못했어요" 안내, 질문 유지, 다시 보내기 가능. 응답이 끊겨 결과를 모를 때는 **같은 요청 번호로** 다시 보내서, 서버가 이미 처리했으면 저장된 답을 돌려줍니다.
근거: `app/static/js/api.js`, `tests/web/test_chat_errors_and_retry.py`

### 실패 후 안전하게 다시 시도할 수 있나 ✅
- 결과를 모르는 실패(연결 끊김) → 같은 요청 번호 → AI 를 두 번 부르지 않음
- 확실한 실패(시간 초과 등) → 새 요청 번호로 새로 시도
- 같은 번호에 다른 질문 → 409 `REQUEST_CONFLICT`

근거: `app/chat/service.py`, 배포 서버 재전송 로그 (EE-23)

### UI/UX 를 고려했나? UI 와 UX 의 차이 ✅
- **UI**(눈에 보이는 화면): 수준 선택 알약 버튼, 말풍선, 전구 캐릭터, 휴대폰 화면, 대비 4.5:1 이상
- **UX**(쓰면서 겪는 경험): 질문 → 답 → 후속 버튼으로 바로 이어 묻기, 오류에도 질문 유지, 기록에서 이어서 질문, 새로고침해도 대화 유지
- **서비스 목적과의 연결:** "수준을 바꿔 가며 이해" 가 목적이라 수준 버튼을 입력칸 위에 항상 두고, 후속 버튼을 답 바로 아래에 둠

근거: `tests/web/README.md`(화면 검증 기록), #56

## 8. 비동기 처리

### `await`, 비동기 원리, 이벤트 루프 🟨
- **`await`**: "이 작업(예: AI 응답)이 끝날 때까지 **이 함수는** 기다리되, 그동안 서버는 다른 요청을 처리해도 된다" 는 표시
- **이벤트 루프**: 기다리는 작업들을 지켜보다가 준비된 것부터 이어서 실행하는 반복. 스레드 하나로 여러 요청을 번갈아 처리
- **우리 코드**: 채팅 API 는 `async def` 이고 AI 호출을 `await provider.generate_reply(...)` 로 기다려서, AI 를 기다리는 몇 초 동안 다른 사용자의 요청을 받을 수 있음
- **한계(알고 있음)**: 같은 `async` 함수 안의 DB 호출은 동기라, DB 를 쓰는 짧은 순간에는 이벤트 루프가 멈춤. 다른 API(`def`)는 FastAPI 가 스레드에서 실행해서 영향이 없음. 규모가 커지면 비동기 DB 드라이버로 바꿔야 함

근거: `app/chat/router.py`, `app/chat/service.py`

### 불필요한 API 요청이 있나 🟨

|---|---|

## 11. LLM

### 답변 품질 개선 노력 ✅
1. 수준별 지침 + 공통 순서(한 줄 정의 → 설명·비유 → 예시 → 핵심 정리) (`app/chat/prompts.py`, #8)
2. 실제 답변을 읽고 보완: 입문자 용어 정의, 해요체 통일, Markdown 대신 일반 텍스트(화면이 글자 그대로 보여 줘서), 비유 일관성 (#46)
3. 배포 서버에서 발견한 "같은 질문을 수준만 바꿔 물으면 문맥을 못 받았다고 답함" 수정 (#54 → #55)
4. 문맥: 같은 대화의 완료된 최근 5턴, 12,000자 예산

### 품질을 어떻게 측정했나 🟨
- **정성 평가** ✅: 같은 질문을 세 수준 + 후속 2개로 실제 AI 에 보내고, 원문을 보존한 뒤 **검토 기준표**(수준 차이, 정의 정확성 — MDN 기준, 비유 일관성, 말투, 형식, 문맥 이어받기)로 사람이 판정. 보완 전·후 비교 (EE-19 15건, #54 6건, EE-23 7건)
- **정량 평가** ❌: 점수화·자동 채점(예: 다른 LLM 으로 채점, 사용자 만족도 버튼)은 하지 않음. 샘플이 한 주제·소수라 일반화하지 않는다고 기록에 적음
