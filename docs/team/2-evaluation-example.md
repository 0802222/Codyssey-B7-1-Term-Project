# 평가 대비 — 예상 진행과 내 코드 설명 준비

팀 평가에서는 퍼실리테이터가 **코드를 같이 보면서 각자에게 맡은 부분을 질문**합니다.
이 문서 하나로 **무엇을 물어볼지, 어떻게 답할지, 어떤 흐름으로 진행될지**를 준비합니다.

- 언제 읽나요: 기능이 어느 정도 만들어진 뒤, 그리고 **평가 1주 전에는 반드시**
- `〔 〕` 칸과 4장의 "내 답변 메모"는 실제 진행 내용으로 채웁니다. 하지 않은 일을 한 것처럼 말하지 않습니다.
- 💡 는 답변 요령, ⚠️ 는 자주 하는 실수입니다.

---

## 1. 평가에서 보는 것

과제 문서의 **"과제 목표"** 6개가 그대로 질문 목록입니다. 각 항목을 누가 주로 설명할지 정해 둡니다.

| # | 과제 목표 ("~을 설명할 수 있다") | 주 설명자 | 보여 줄 코드 |
|---|---|---|---|
| 1 | FastAPI 웹 서비스 구성 (라우팅, 요청/응답, 템플릿·프런트 연동) | **L** + C | `app/main.py`, `app/*/router.py`, `app/templates/` |
| 2 | 회원가입/로그인, 인증 상태에 따른 접근 제어의 이유와 방식 | **A** | `app/auth/` |
| 3 | 질문 수신 → AI 호출 → 응답 반환 → 대화 로그 저장 파이프라인 | **B** | `app/chat/` |
| 4 | 대화 로그를 DB 에 누적하고 사용자 기준으로 조회·추적하는 설계 | **A** | `app/db/models.py`, `app/conversations/`, `scripts/` |
| 5 | AI 실패·타임아웃에서 서비스가 죽지 않게 처리, 로그로 원인 추적 | **B** + L | `app/chat/provider.py`, `app/core/errors.py`, `app/core/logging.py` |
| 6 | 브랜치 전략, PR 협업, 문서화로 품질 유지 | **L** + 전원 | GitHub PR 목록, `CONTRIBUTING.md`, `.github/` |

**주의:** "주 설명자"가 아니어도 **전원이 1번(전체 흐름)과 6번(내 PR·커밋)은 답할 수 있어야** 합니다.

## 2. 답변 요령

어떤 질문이든 이 순서로 답하면 짧고 명확합니다.

```
① 한 줄 요약     "로그인한 사람만 채팅 API 를 쓸 수 있게, 모든 요청에서 세션 쿠키를 서버가 확인합니다."
② 코드 보여주기   파일을 열고 핵심 줄을 가리키며 "여기서 쿠키를 읽고, 여기서 만료를 확인합니다."
③ 증명하기       "테스트로 확인했습니다" → 테스트 코드나 실제 화면·로그를 보여 줌
```

- **"왜"를 꼭 붙입니다.** "비밀번호를 해시로 저장합니다"보다 "DB 가 유출돼도 원래 비밀번호를 알 수 없게 해시로 저장합니다"가 좋은 답입니다.
- **모르는 건 모른다고 합니다.** 대신 "그 부분은 B 가 담당했고, 제 코드는 B 의 이 함수를 호출합니다"처럼 연결 지점은 설명합니다.
- **AI 도구로 만든 코드도 내 코드입니다.** 줄마다 무슨 일을 하는지 말할 수 없는 코드는 커밋 전에 이해하고 넘어갑니다.

### 꼬리 질문 대비

퍼실리테이터는 답을 듣고 한 단계 더 물어봅니다. 자주 나오는 형태입니다.

- "그 코드를 지우면 어떻게 되나요?" → 그 줄이 막고 있는 문제를 설명
- "다른 방법은 없었나요? 왜 이 방법을 골랐나요?" → 예: JWT 대신 서버 세션 (로그아웃 시 즉시 무효화 가능)
- "그게 정말 동작하는지 어떻게 아나요?" → 테스트 이름이나 시연으로 증명
- "실패하면 로그에 뭐가 남나요?" → 실제 로그 한 줄을 보여 줌
- "사용자가 많아지면 문제가 뭘까요?" → SQLite 단일 파일, 단일 인스턴스 한계를 알고 있음을 보여 줌

### 요청 하나의 흐름 (전원이 설명할 수 있어야 함)

```
브라우저 (C)  ── POST /api/chat ──▶  FastAPI
                                     │
  ① RequestIdMiddleware (L)          요청 ID 발급, request_received 로그
  ② 인증 의존성 (A)                   세션 쿠키 확인 → 로그인 사용자 / 아니면 401
  ③ 입력 검증 (B)                     빈 질문·길이·level 확인 → 아니면 422
  ④ 질문 저장 (A 의 저장소, B 가 호출)   status=pending
  ⑤ 최근 대화 5턴 조회 (B)              문맥 구성
  ⑥ AI 호출 (B)                       ai_call_start → 성공/실패/타임아웃 로그
  ⑦ 응답 저장 (A 의 저장소)             status=completed, db_save_success 로그
  ⑧ 오류면 공통 오류 처리기 (L)          {"error": {code, message, request_id}}
                                     │
브라우저 (C)  ◀── 답변 또는 오류 안내 ──┘  화면에 표시
```

## 3. 예상 진행 대본

실제 질문은 달라질 수 있습니다. 문장을 외우지 말고 **흐름과 답변 포인트**를 익히세요.

### 등장인물

| | 이름 | 담당 |
|---|---|---|
| 🧑‍🏫 | **퍼실** | 퍼실리테이터 (평가자) |
| 👑 | **L** 이초롱 | 팀장 · 공통 뼈대, 오류·로그, CI, 통합, 배포 |
| 🔐 | **A** 송지윤 | 회원·로그인·접근 제어, DB, 내 기록 |
| 🤖 | **B** 나현준 | AI 호출, 설명 수준, 문맥 유지, AI 오류 |
| 🎨 | **C** 유민규 | 웹 화면, API 연결, 사용성 |

### 전체 흐름 (약 30~40분 예상)

```
1. 과제 소개 (L)            3분
2. 팀·진행 개요 토크 (전원)    7분
3. 서비스 시연 (C 진행)       5분
4. 기능별 질의응답            각 5~7분
   🔐 A 인증·DB → 🤖 B AI·채팅 → 🎨 C 화면 → 👑 L 공통·협업·배포
5. Git 기록 확인 (전원)       3분
6. 마무리·회고 (전원)         3분
```

### 3-1. 과제 소개

**🧑‍🏫 퍼실:** 안녕하세요. 먼저 팀장님이 어떤 서비스를 만들었는지 소개해 주시겠어요?

**👑 L:** 네. 저희 팀은 **EasyExplain** 이라는 학습용 AI 챗봇을 만들었습니다.
모르는 개념을 물어보면 "아주 쉽게 / 입문자 / 전공자" 세 가지 수준 중 하나로 설명해 주고,
"더 쉽게", "예시 하나 더" 같은 후속 질문을 하면 앞 대화를 기억해서 이어서 설명해 줍니다.

과제 요구사항인 **로그인한 사용자만 질문 → 서버에서 AI 호출 → 답변 표시 → DB 저장 → 내 기록 조회** 흐름을
그대로 따르고, 그 위에 설명 수준과 후속 버튼을 저희 주제로 얹었습니다.
서비스는 〔서비스 URL〕 에 배포되어 있습니다.

**🧑‍🏫 퍼실:** 왜 이 주제를 골랐나요?

**👑 L:** 개발 공부를 시작할 때 "API", "배포" 같은 용어 설명이 너무 어렵게 느껴졌던 경험이 있었습니다.
같은 개념도 사람마다 필요한 깊이가 달라서, **수준을 바꿔 가며 다시 물어볼 수 있는 챗봇**이면 좋겠다고 생각했습니다.
또 과제 필수 기능인 "문맥 유지"가 "더 쉽게 설명해줘" 같은 후속 질문에서 자연스럽게 드러나는 주제라서 골랐습니다.

> 💡 소개는 **무엇을 → 누구를 위해 → 과제 요구와 어떻게 연결되는지** 순서로 1분 안에.
> ⚠️ 기술 스택부터 나열하지 않습니다. 기술은 질문이 오면 설명합니다.

### 3-2. 팀·진행 개요 토크

**🧑‍🏫 퍼실:** 역할은 어떻게 나눴나요?

**👑 L:** 서비스를 부품으로 나눠서, 한 사람이 한 영역을 처음부터 끝까지 책임지게 했습니다.
저는 앱 뼈대, 공통 오류 처리와 로그, CI, 배포를 맡았고요.

**🔐 A:** 저는 회원가입·로그인과 접근 제어, 그리고 대화 기록을 저장하고 조회하는 DB 쪽을 맡았습니다.

**🤖 B:** 저는 AI 를 호출하는 부분, 설명 수준별 프롬프트, 이전 대화를 기억하는 문맥 유지, AI 오류 처리를 맡았습니다.

**🎨 C:** 저는 사용자가 보는 화면 전체와, 화면에서 서버 API 를 호출하는 부분을 맡았습니다.

**🧑‍🏫 퍼실:** 나눠서 만들면 합칠 때 문제가 생기지 않았나요?

**👑 L:** 그걸 막으려고 **코드를 쓰기 전에 API 명세와 DB 구조를 먼저 문서로 합의**했습니다. (`docs/spec/api.md`)
그리고 제가 뼈대를 만들 때 영역 사이의 연결 지점을 미리 정해 뒀습니다.
예를 들어 B 는 A 의 로그인이 완성되기 전에도 "로그인 사용자는 `CurrentUserDep` 로 받는다"는 약속만 보고 개발할 수 있었습니다.

**🤖 B:** 저도 실제 AI 키 없이 **가짜 AI(Fake provider)** 로 먼저 개발하고 테스트한 다음에, 마지막에 실제 Claude 로 바꿨습니다.

**🧑‍🏫 퍼실:** 기간은 얼마나 걸렸고, 어떻게 진행했나요?

**👑 L:** 〔시작일〕부터 〔종료일〕까지 약 〔N〕주 진행했습니다. 크게 다섯 단계였습니다.

| 단계 | 기간 | 한 일 |
|---|---|---|
| 기반 | 〔 〕 | 저장소·규칙·API 계약, 서버 뼈대 |
| 기능 | 〔 〕 | 각자 영역을 병렬 개발 (가짜 AI·고정 응답 활용) |
| 통합 | 〔 〕 | 로그인 → 질문 → 저장 전체 연결 |
| 검증 | 〔 〕 | 오류·권한·입력 검증 테스트 |
| 배포·문서 | 〔 〕 | 외부 배포, README, 발표 준비 |

**🧑‍🏫 퍼실:** 만나서 작업했나요, 온라인으로 했나요?

**👑 L:** 〔예: 주 N회 오프라인으로 만나고, 나머지는 온라인으로 진행했습니다.〕
매일 시작할 때 10분 정도 어제 한 것, 오늘 할 이슈, 막힌 점을 공유했고,
작업은 GitHub 이슈로 나누고 **모든 변경은 PR 로 올려서 다른 팀원 1명이 리뷰·승인한 뒤에만 머지**했습니다.

**🧑‍🏫 퍼실:** 진행하면서 어려웠던 점은요?

**👑 L:** 〔실제 경험으로 1개. 예: 처음에 각자 오류 응답 형식이 달라서 화면에서 처리하기 어려웠는데,
공통 오류 형식을 정하고 `AppError` 하나로 통일해서 해결했습니다. → 관련 PR #〔 〕〕

**🎨 C:** 〔예: 백엔드가 완성되기 전에 화면을 만들어야 해서, API 명세의 응답 예시로 먼저 화면을 만들고
나중에 실제 API 로 바꿨습니다.〕

> 💡 어려움은 **문제 → 원인 → 해결 → 증거(PR·커밋)** 로 말합니다.
> ⚠️ "딱히 없었습니다"는 피합니다. 작은 것이라도 실제 겪은 일을 준비합니다.

### 3-3. 서비스 시연

**🧑‍🏫 퍼실:** 실제로 동작하는 걸 보여 주시겠어요?

**🎨 C:** 네, 배포된 URL 로 보여 드리겠습니다.

```
① 로그인 안 한 상태로 /chat 접속 → 로그인 페이지로 이동되는 것 확인
② 테스트 계정으로 로그인
③ 수준 "아주 쉽게" 선택 → "API가 뭐야?" 질문 → 답변 표시 (대기 중 버튼 잠김)
④ 수준을 "전공자"로 바꿔 같은 질문 → 설명 깊이가 달라지는 것 확인
⑤ "그걸 음식점에 비유해줘" → 앞의 API 주제를 기억하고 답변
⑥ 내 기록 → 방금 대화가 저장된 것 확인 → 새로고침해도 유지
```

**🧑‍🏫 퍼실:** 빈 질문을 보내면요?

**🎨 C:** 화면에서도 막고, 서버에서도 한 번 더 막습니다. 화면 검사를 우회해도 서버가 `422` 와 안내 메시지를 돌려줍니다.

> 💡 시연은 **필수 기능 → 우리 주제 기능 → 실패 상황** 순서로.
> ⚠️ 시연 화면에 실제 이메일, API 키, 개발자 도구의 쿠키 값이 보이지 않게 합니다.

### 3-4. 기능별 질의응답

#### 🔐 A — 회원가입·로그인, 접근 제어, 대화 기록 DB

**🧑‍🏫 퍼실:** A 님, 회원가입 코드를 보여 주세요. 비밀번호는 어떻게 저장하나요?

**🔐 A:** `app/auth/` 의 〔파일명〕 입니다. 비밀번호는 평문으로 저장하지 않고 **Argon2 라는 방식으로 해시**해서 저장합니다.
해시는 되돌릴 수 없어서, DB 가 유출되더라도 원래 비밀번호를 알 수 없습니다.
로그인할 때는 입력한 비밀번호를 같은 방식으로 검증만 합니다.

**🧑‍🏫 퍼실:** 로그인 상태는 어떻게 유지하죠?

**🔐 A:** 로그인에 성공하면 서버가 무작위 토큰을 만들어서 **브라우저에는 HttpOnly 쿠키**로 주고,
**DB 에는 그 토큰의 해시와 만료 시각**을 저장합니다. 이후 요청마다 서버가 쿠키를 DB 와 비교해서 로그인 사용자를 찾습니다.

**🧑‍🏫 퍼실:** HttpOnly 는 왜 쓴 건가요?

**🔐 A:** 자바스크립트에서 쿠키를 읽을 수 없게 하는 옵션입니다. 혹시 화면에 악성 스크립트가 들어와도 로그인 토큰을 훔쳐 갈 수 없습니다.

**🧑‍🏫 퍼실:** 로그인 안 한 사람이 채팅 API 를 직접 호출하면요?

**🔐 A:** 채팅 API 는 함수 인자에 `CurrentUserDep` 를 받게 되어 있어서, 로그인 확인을 통과하지 못하면 함수가 실행되기 전에
`401 AUTH_REQUIRED` 가 나갑니다. 테스트로 확인했습니다. → `tests/auth/〔테스트명〕`

**🧑‍🏫 퍼실:** 다른 사람의 대화 ID 를 알아내서 조회하면 볼 수 있나요?

**🔐 A:** 볼 수 없습니다. 대화를 조회할 때 **대화 ID 와 함께 항상 로그인 사용자 ID 를 조건으로** 겁니다.
그리고 남의 대화든 없는 대화든 **똑같이 404** 를 돌려줘서, 그 대화가 존재하는지조차 알 수 없게 했습니다.

**🧑‍🏫 퍼실:** 대화 기록은 DB 에 어떻게 저장되나요? 사용자별로 어떻게 확인하죠?

**🔐 A:** `chat_turns` 테이블에 질문 하나와 답변 하나를 한 줄로 저장합니다.
과제 최소 필드인 사용자 ID, 생성 시각, 질문, 답변에 더해 대화 ID, 설명 수준, 처리 상태도 저장합니다.
확인은 두 가지 방법이 있습니다. 로그인한 사용자는 `GET /api/me/chats` 로 자기 기록을 보고,
운영자는 `scripts/check_logs.sql` 로 사용자별 최근 기록을 조회할 수 있습니다.

> 💡 보안 질문은 **"무엇을 막는지"** 를 먼저 말하면 답이 명확해집니다.

---

#### 🤖 B — AI 호출, 문맥 유지, AI 오류 처리

**🧑‍🏫 퍼실:** B 님, 질문 하나가 들어오면 서버에서 어떤 순서로 처리되나요?

**🤖 B:** `app/chat/` 의 〔파일명〕 기준으로 설명드리겠습니다.

```
① 입력 검증 (빈 질문, 2,000자, level 값)
② 질문을 "처리 중(pending)" 상태로 먼저 저장
③ 같은 대화의 최근 5턴을 DB 에서 조회
④ 시스템 지침 + 이전 대화 + 현재 질문으로 AI 호출 (최대 30초)
⑤ 성공하면 답변을 저장하고 "완료(completed)"로 변경 → 화면에 반환
   실패하면 "실패(failed)"와 오류 코드를 저장 → 오류 안내 반환
```

**🧑‍🏫 퍼실:** AI 호출을 브라우저에서 바로 하면 더 간단하지 않나요?

**🤖 B:** 그러면 브라우저에 API 키가 들어가야 해서 누구나 키를 볼 수 있게 됩니다.
그래서 **AI 호출은 서버에서만** 하고, 키는 서버의 `.env` 에만 있습니다. 브라우저는 결과 텍스트만 받습니다.

**🧑‍🏫 퍼실:** 문맥 유지는 어떻게 구현했나요?

**🤖 B:** 같은 대화에서 **완료된 최근 5턴**을 오래된 순서로 `질문, 답변, 질문, 답변…` 배열로 만들고, 마지막에 현재 질문을 붙여서 AI 에 보냅니다.
실패한 턴은 넣지 않습니다. 그래서 "그걸 음식점에 비유해줘"라고 하면 앞에서 물어본 API 를 알고 답할 수 있습니다.

**🧑‍🏫 퍼실:** 왜 5턴인가요? 대화가 아주 길어지면요?

**🤖 B:** 많이 보낼수록 응답이 느려지고 비용이 늘어서, 후속 질문에 충분한 정도로 5턴을 골랐습니다.
그래도 너무 길면 과거 대화가 12,000자를 넘을 때 가장 오래된 것부터 뺍니다. 두 값 모두 설정으로 바꿀 수 있습니다.

**🧑‍🏫 퍼실:** 새 대화를 시작하면 이전 대화 내용이 섞이지 않나요?

**🤖 B:** 문맥은 **같은 대화 ID** 안에서만 가져오기 때문에 섞이지 않습니다. 이 부분은 테스트로 확인했습니다. → `tests/chat/〔테스트명〕`

**🧑‍🏫 퍼실:** AI 가 응답을 안 주면 어떻게 되나요?

**🤖 B:** 30초 타임아웃을 걸어 두었습니다. 시간이 넘으면 `504 AI_TIMEOUT` 과 "응답이 지연되고 있어요" 안내를 돌려주고,
그 질문은 실패 상태로 저장합니다. **서버는 죽지 않고 다음 요청을 계속 받습니다.**
자동 재시도는 하지 않습니다. 재시도하면 사용자가 더 오래 기다리고 비용도 늘어서, 다시 시도는 사용자가 직접 하게 했습니다.

**🧑‍🏫 퍼실:** 그 상황을 실제로 어떻게 확인했나요?

**🤖 B:** 실제 AI 를 일부러 느리게 만들 수는 없어서, **가짜 AI 가 타임아웃을 내도록** 한 테스트로 확인했습니다.
서버 로그에는 같은 요청 ID 로 `ai_call_start` 다음에 `ai_call_failed` 가 남습니다.

> 💡 "왜 이렇게 했나"에는 **다른 선택지와 비교**해서 답하면 좋습니다. (브라우저 호출 vs 서버 호출, 재시도 vs 미재시도)

#### 🎨 C — 화면, API 연결, 사용성

**🧑‍🏫 퍼실:** C 님, 화면은 어떻게 만들었나요? React 같은 걸 썼나요?

**🎨 C:** 별도 프런트엔드 프레임워크 없이, FastAPI 가 **Jinja2 템플릿**으로 HTML 을 내려주고
채팅 부분만 자바스크립트 `fetch` 로 `/api/chat` 을 호출합니다. 서버 하나로 화면과 API 를 함께 제공해서 배포가 단순합니다.

**🧑‍🏫 퍼실:** 질문하면 답이 같은 화면에 어떻게 나오죠?

**🎨 C:** 페이지를 새로 불러오지 않고, 자바스크립트가 서버 응답 JSON 을 받아 대화 영역 아래에 추가합니다. 〔파일명·함수명〕 입니다.

**🧑‍🏫 퍼실:** 답변을 기다리는 동안 전송 버튼을 여러 번 누르면요?

**🎨 C:** 대기 중에는 버튼을 비활성화하고 "답변을 만드는 중" 표시를 띄웁니다.
그리고 요청마다 고유 ID 를 같이 보내서, 혹시 같은 요청이 두 번 가도 서버가 AI 를 두 번 호출하지 않습니다.

**🧑‍🏫 퍼실:** AI 답변에 `<script>` 같은 게 섞여 오면 위험하지 않나요?

**🎨 C:** 답변을 `innerHTML` 이 아니라 **`textContent`** 로 넣어서, HTML 이 아니라 글자로만 표시됩니다. 스크립트가 실행되지 않습니다.

**🧑‍🏫 퍼실:** 오류가 나면 사용자는 뭘 보게 되나요?

**🎨 C:** 서버의 모든 오류가 `{"error": {"code", "message"}}` 같은 형식으로 오기 때문에, 화면은 `message` 를 그대로 안내로 보여 줍니다.
입력한 질문은 지우지 않고 버튼도 다시 활성화해서 바로 다시 보낼 수 있게 했습니다.

**🧑‍🏫 퍼실:** 로그인 안 한 사람한테 채팅 메뉴를 숨기면 충분하지 않나요?

**🎨 C:** 숨기는 건 보기 좋게 하는 것일 뿐이고, 주소를 직접 입력하면 들어올 수 있습니다.
그래서 **실제 권한 검사는 서버**가 하고, 화면은 서버가 401 이나 로그인 이동을 주면 그대로 따릅니다.

> 💡 화면 담당도 **보안·오류 처리**를 질문받습니다. "서버가 막는다 + 화면은 어떻게 반응한다"를 함께 설명합니다.

#### 👑 L — 앱 구조, 공통 처리, 협업, 배포

**🧑‍🏫 퍼실:** 팀장님, FastAPI 앱 전체 구조를 코드로 설명해 주세요.

**👑 L:** `app/main.py` 의 `create_app()` 입니다.
설정을 읽고 → DB 연결을 만들고 → 요청 ID 미들웨어와 공통 오류 처리기를 붙이고 → 영역별 라우터를 연결합니다.
각 영역은 자기 폴더에 라우터를 두고, 여기서 `include_router` 로 조립만 합니다.

**🧑‍🏫 퍼실:** 과제에서 요구한 서버 로그는 어디서 남기나요?

**👑 L:** 요청이 들어오면 `core/middleware.py` 가 **서버에서 요청 ID 를 발급**하고 `request_received` 를 남깁니다.
그다음 B 의 AI 호출, A 의 DB 저장도 `log_event()` 하나로 남기는데, 이 함수가 요청 ID 를 자동으로 붙입니다.
그래서 로그에서 요청 ID 하나로 검색하면 **요청 수신 → AI 호출 → AI 성공·실패 → DB 저장 성공·실패**가 한 줄로 이어집니다.

```
INFO request_received request_id=a1b2… method=POST path=/api/chat
INFO ai_call_start    request_id=a1b2… user_id=12 model=…
INFO ai_call_success  request_id=a1b2… latency_ms=1240
INFO db_save_success  request_id=a1b2… user_id=12 turn_id=31
```

**🧑‍🏫 퍼실:** 로그에 질문 내용이나 비밀번호가 남지는 않나요?

**👑 L:** 남기지 않도록 규칙으로 정했습니다. 비밀번호, 쿠키, 토큰, API 키, 질문·답변 원문은 로그에 쓰지 않습니다.
질문·답변은 접근이 통제된 DB 에만 저장합니다. 입력 검증 실패 로그도 값이 아니라 **문제가 된 필드 이름만** 남깁니다.

**🧑‍🏫 퍼실:** 예상하지 못한 에러가 나면 서버가 죽나요?

**👑 L:** 아니요. 공통 오류 처리기가 잡아서 `500 INTERNAL_ERROR` 와 안내 메시지를 돌려줍니다.
에러 상세 내용은 서버 로그에만 남기고 사용자에게는 보여 주지 않습니다. `tests/core/test_errors.py` 에서 확인합니다.

**🧑‍🏫 퍼실:** API 키 같은 민감정보는 어떻게 관리했나요?

**👑 L:** 키는 `.env` 에만 두고 `.gitignore` 로 저장소에 안 올라가게 했고, 대신 이름만 있는 `.env.example` 을 제공합니다.
설정 코드에서 키는 `SecretStr` 이라 실수로 출력해도 가려집니다.
또 **운영 환경에서 가짜 AI 로 켜지거나 키가 없으면 서버가 아예 시작되지 않게** 막아 두었습니다.

**🧑‍🏫 퍼실:** 브랜치 전략과 PR 규칙을 설명해 주세요.

**👑 L:** main 과 기능 브랜치 구조입니다. 이슈마다 `feat/ee-08-auth-session` 같은 브랜치를 만들고 PR 로만 main 에 들어갑니다.
main 은 보호 규칙으로 **직접 push 금지, 다른 팀원 1명 승인 필수, 리뷰 대화 해결 필수, CI 통과 필수**로 설정했습니다. 팀장인 저도 예외가 아닙니다.
병합은 **Merge commit 만** 허용했습니다. Squash 를 쓰면 개인 커밋이 하나로 합쳐져서 각자의 작업 기록이 사라지기 때문입니다.

**🧑‍🏫 퍼실:** CI 는 무엇을 하나요?

**👑 L:** PR 이 올라오면 GitHub Actions 가 코드 검사(ruff)와 자동 테스트(pytest)를 돌립니다.
CI 에는 실제 AI 키를 넣지 않고 가짜 AI 와 임시 DB 로 테스트합니다.

**🧑‍🏫 퍼실:** 배포는 어떻게 했고, 서버를 재시작하면 데이터가 남나요?

**👑 L:** 〔배포 플랫폼·방법〕 으로 배포했습니다. SQLite 는 파일이라서, 재시작해도 지워지지 않는 〔영속 저장 경로〕 에 DB 파일을 둡니다.
재배포 후에도 기존 계정과 대화가 남아 있는 것을 확인했습니다. 〔확인 날짜·방법〕

> ⚠️ 배포·재시작 검증은 **실제로 해 본 것만** 말합니다. 안 해 봤으면 "아직 확인하지 못했다"고 합니다.
