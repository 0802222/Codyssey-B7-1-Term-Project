# EE-23: 배포 환경 AI 검증

관련 이슈: [#30](https://github.com/easy-explain/Codyssey-B7-1-Term-Project/issues/30).
검증 대상: https://codyssey-b7-1-term-project-production.up.railway.app

EE-19는 임시 DB에서 채팅 서비스를 직접 실행했습니다. EE-23은 배포 서버의
회원가입·로그인·대화 생성·채팅·기록 조회 API를 HTTP로 호출합니다.
새 테스트 계정에는 임의의 자격증명을 사용하고, 비밀번호·이메일·쿠키·CSRF 토큰은
증빙 파일에 넣지 않습니다. 공개 샘플 질문만 사용합니다.

## 1차 답변 수집 (완료, 재실행하지 않음)

수집 도구는 `deployment_check.py`입니다. 별도의 AI 키 없이 배포 서버에 로그인해 호출합니다.
기본 5건 모드는 테스트 계정과 대화 3개를, 시간 초과·복구 모드는 계정과 대화 1개를 서버에 만듭니다.
운영 데이터는 삭제하지 않습니다.
이미 존재하는 출력 파일은 덮어쓰지 않으며, 오류가 나면 완료한 기록을 보존하고 중단합니다.
아래 명령은 기존 1차 수집의 사용법입니다. 최종 배포의 남은 검증에서는 5건을 다시 수집하지 않습니다.

```bash
uv run --locked python -m app.chat.deployment_check \
  --live \
  --base-url https://codyssey-b7-1-term-project-production.up.railway.app \
  --output app/chat/samples/ee-23-실행일.json
```

EE-19와 같은 질문을 독립된 새 대화에서 easy·beginner·advanced로 보냅니다.
advanced 대화에서는 현재 수준을 easy로 바꿔 “더 쉽게”, “예시 하나 더”를 보냅니다.
최대 5회의 신규 질문만 전송하고 자동 재시도를 하지 않습니다.
첫 완료 요청을 같은 키로 한 번 재전송해 같은 턴이 반환되는지 확인합니다.
API 관측만으로 AI 재호출 여부를 직접 증명하지 않으므로 운영 로그도 확인해야 합니다.

각 응답의 본문 `request_id`와 헤더 `X-Request-ID`를 함께 보존합니다.
새 요청은 둘이 같고, 완료 재전송은 본문에 최초 요청 ID가 남고 헤더에는 새 HTTP 요청 ID가 생깁니다.
저장된 상세 기록의 턴 ID·수준·질문·답변·상태도 응답과 비교합니다.

### 수동 품질 검토

실제 수집 후 원문을 고치지 않고, 수준 차이·주제 유지·현재 easy 적용·해요체·일반 텍스트·완결성을 검토했습니다.
API 정의의 비교 기준은 [MDN API 설명](https://developer.mozilla.org/en-US/docs/Glossary/API)입니다.
비유는 개념 이해용이고, 특정 서비스의 실제 동작을 검증한 것으로 보지 않습니다.

| 항목 | 관찰 결과 |
|---|---|
| 수준 차이 | easy는 식당·웨이터 비유, beginner는 요청→응답→화면의 흐름, advanced는 인터페이스 명세·추상화·API 종류 설명 |
| 후속 질문 | C의 두 후속 답변 모두 API 주제를 이어가며 쉬운 식당·로그인 예시 사용. 현재 easy 요청과 저장된 수준 일치 |
| 말투·완결성 | 5건 모두 해요체이며 문장상 잘림 없음 |
| 일반 텍스트 | 표·강조·코드펜스는 없으나 B-beginner와 C-easier에 `-` 목록이 있음. 번호 목록만 쓰도록 한 지침을 완전히 지킨 결과로 보지는 않음 |
| 비유 일관성 | C-easier는 첫 문장의 “주문서”에서 본문의 “메뉴판”으로 비유 대상이 바뀜. 개선이 필요한 관찰로 원문 보존 |
| 초보 용어 | B-beginner는 요청·응답 흐름을 보여 주지만 각각의 용어 정의를 따로 풀지는 않음. 수준 차이가 모든 항목에서 충분하다고 판정하지 않음 |
| 실제 서비스 예시 | C-example의 카카오 로그인은 개념 설명으로 단순화됨. 인증·동의·인가 코드·토큰·사용자 조회 등 실제 절차 전체의 검증 자료가 아님 |

[카카오 로그인 공식 절차](https://developers.kakao.com/docs/ko/kakaologin/rest-api#before-you-begin-process)는
인가 코드 요청, 토큰 요청, 서비스의 사용자 로그인 처리를 구분합니다.
모델 답변은 실제 구현 안내로 그대로 사용하지 않습니다.
프롬프트가 이미 요구하는 비유·형식 지침도 모델이 항상 지키는 것은 아니므로,
이번 5건을 근거로 모든 질문의 품질을 보장하지 않습니다. 답변 원문이나 기존 프롬프트는 수정하지 않았습니다.

## 시간 초과·복구 점검 순서

팀장은 개발·평가용 서버이므로 별도 DB 대신 기존 production에서 점검한다고 정했습니다.
점검 동안 다른 팀원은 질문을 보내지 않으며, 코드 기준은 최종 커밋 `03f84e6`입니다.
정상 설정은 `anthropic` / `claude-sonnet-4`, `AI_TIMEOUT_SECONDS=30`, replica 1·worker 1이라고
운영자가 확인했습니다. 복구 때는 환경변수를 삭제하지 않고 **명시적으로 30을 설정**합니다.

| 순서 | 담당·작업 | 상태 |
|---|---|---|
| 1 | 팀장: `AI_TIMEOUT_SECONDS=1` 적용·재배포 | 사용자 전달 신호로 완료 확인, Railway 배포 `4164ad34` |
| 2 | B: `--expect-timeout` 신규 1건·같은 키 재전송·저장·health 확인 | 완료, 아래 HTTP 원본 |
| 3 | 팀장: `AI_TIMEOUT_SECONDS=30` 복구·재배포·완료 신호 | 팀장 코멘트로 완료 확인, 복구 배포 ID는 제공되지 않음 |
| 4 | B: 복구 신호 후 `--check-recovery` 신규 1건·같은 키 재전송·저장·health 확인 | 완료, 아래 HTTP 원본 |

`4164ad34`와 적용 설정은 운영자 보고이며, 공개 API로 직접 읽은 런타임 값이 아닙니다.
서버 시작의 `init_db()`는 모든 `pending` 턴을 `interrupted`로 바꾸므로, 같은 DB를 쓰는
테스트 앱이나 두 worker를 동시에 띄우지 않습니다. **504·failed 저장·재전송 증빙을 확보한 뒤
팀장이 복구 재배포합니다.** 점검을 위해 긴 질문이나 연결 끊기로 실패를 유도하지 않습니다.

## request_id로 서버 로그 확인

수집 파일에 기록한 최초 POST의 헤더 요청 ID로 Railway 로그를 검색합니다.
공개 기록에는 아래 이벤트의 ID·시각·상태·오류 코드만 옮깁니다.
로그 원본의 사용자 ID·이메일·쿠키·키·질문·답변은 넣지 않습니다.

```text
request_received
db_save_success status=pending
ai_call_start
ai_call_success 또는 ai_call_failed error_code=AI_TIMEOUT
db_save_success status=completed 또는 status=failed
request_completed status=200 또는 status=504
```

위는 공통 기대 순서입니다. 시간 초과의 실측 로그는 팀장이 요청 ID별로 검색해 코멘트로
제공했습니다. 직접 콘솔에서 내보낸 원본과 구분하며 사용자 식별자를 제외한
[시간 초과 로그 기록](samples/ee-23-2026-10-11-timeout-logs.json)으로 보존했습니다.
최초 요청은 `request_received` → pending 저장 → `ai_call_start` → `AI_TIMEOUT` 실패 →
failed 저장 → 504 종료의 6개 이벤트이며, 서버 처리 시간은 2,264ms였습니다.
AI 시작부터 실패까지는 로그상 약 1.002초입니다. 같은 키 재전송은 수신·504 종료의 2개 이벤트,
4ms이며, 팀장이 요청 ID로 검색한 결과 추가 AI 시작 이벤트가 없다고 확인했습니다.

복구 로그도 팀장이 요청 ID별로 검색해 코멘트로 제공했습니다.
[복구 로그 기록](samples/ee-23-2026-10-11-recovery-logs.json)에 출처와 직접 콘솔 접근 여부를 남겼습니다.
최초 복구 요청은 수신 → pending 저장 → AI 시작 → AI 성공 → completed 저장 → 200 종료의
6개 이벤트이며, 서버 처리 시간은 11,626ms였습니다. AI 시작부터 성공까지는 **10.371초**로,
운영자가 보고한 30초 제한 안이었습니다. 같은 키 재전송은 수신·200 종료의 2개 이벤트,
8ms이며 추가 `ai_call_start`가 없다고 운영자가 확인했습니다.

| 대상 | POST의 `X-Request-ID` | 확인 시각(KST) | 로그에서 확인한 흐름·HTTP 상태 | 근거 링크·기록 위치 |
|---|---|---|---|---|
| 최종 배포 기준 시간 초과 | `f5a25126364a4a9a877b905b429fd279` | 00:46:39 | pending→AI 시작→AI_TIMEOUT→failed→504, 2,264ms | [팀장 제공 로그](samples/ee-23-2026-10-11-timeout-logs.json) |

## 키 한도와 횟수 제한 제안

현재 코드 기본값은 사용자 최근 60초 10회, 서비스 전체 UTC 하루 200회입니다.
서버의 요청 제한은 게이트웨이 키의 남은 예산과 다릅니다.
실패한 AI 시도도 횟수를 쓰며, 완료·실패 재전송은 새 AI 호출 횟수를 쓰지 않습니다.
이 제한은 단일 worker·단일 인스턴스 메모리에 있으며 재시작하면 초기화됩니다.
따라서 하루 200회를 키 사용량의 강제 상한으로 간주할 수 없습니다.

EE-19 최신 5건은 총 8,451토큰, 평균 약 1,690토큰이었습니다.
이는 소수 로컬 표본의 응답 메타데이터이며, 이번 배포의 사용량·청구 단위·최대 비용이 아닙니다.
대화 문맥이 길어지면 입력 사용량도 늘어납니다.

팀장은 2026-10-11 코디세이 콘솔 기준 키 1개의 아래 숫자를 제공했습니다.
원문 화면을 직접 본 것은 아니며, [운영자 제공 기록](samples/ee-23-2026-10-11-operator-confirmation.json)에
출처와 확인 한계를 함께 남겼습니다. 수치는 **00:44:58 KST에 수정된 팀장 코멘트 기준**으로,
시간 초과·복구 신규 2건을 실행하기 전 자료입니다. 현재 잔여량으로 갱신한 값은 아닙니다.
기존 기록의 당시 대기 상태는 원본에 보존하고, 이후 완료 증빙은 이 문서와 각 로그 파일로 연결합니다.

| 항목 | 운영자 제공 값·확인 범위 |
|---|---|
| 월 사용 호출 | 30회 |
| 차감 토큰 | 61,968토큰, 입력+출력 기준·캐시 0으로 안내 |
| 잔여 토큰 | 4,938,032토큰 |
| 호출당 평균 | 2,065.6토큰, 약 2,070토큰 |
| 초기화 | 매월 1일로 기억한다고 안내, 실제 초기화 시각·시간대는 미확인 |
| 모델 가중치·공유·시연 여유 예산 | 적용 방식·공유 범위·별도 확보량은 미확인 |
| 최종 횟수 제한 제안 | **사용자 최근 60초 10회·서비스 UTC 하루 200회 유지**, 팀장 동의 |

평균 2,070토큰으로 단순 계산하면 하루 200회는 약 414,000토큰입니다.
이는 사용 규모를 이해하기 위한 **평균 예시**이며 최대 사용량·안전 예산을 보장하지 않습니다.
문맥 길이·출력 길이·실패 시 과금에 따라 실제 소모가 달라질 수 있어 기존 제한을 올리지 않습니다.
실제 초기화 시간대·가중치·다른 작업 사용량이 확인되지 않은 만큼 장기간 잔여량을 예측하지 않습니다.
특히 재시작 시 메모리 횟수 제한이 초기화되므로, 200회를 청구 한도로 간주하지 않습니다.
운영자는 콘솔 사용량을 보며 시연에 필요한 여유를 남기고, 부족하면 신규 질문을 중단합니다.
공유 범위·최대 1회 비용·시연 예산의 미확인은 현재 제안의 한계로 남깁니다.
