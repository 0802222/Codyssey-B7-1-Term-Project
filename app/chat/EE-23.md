## 1차 답변 수집 (완료, 재실행하지 않음)

수집 도구는 `deployment_check.py`입니다. 별도의 AI 키 없이 배포 서버에 로그인해 호출합니다.
기본 5건 모드는 테스트 계정과 대화 3개를, 시간 초과·복구 모드는 계정과 대화 1개를 서버에 만듭니다.
운영 데이터는 삭제하지 않습니다.
이미 존재하는 출력 파일은 덮어쓰지 않으며, 오류가 나면 완료한 기록을 보존하고 중단합니다.
아래 명령은 기존 1차 수집의 사용법입니다. 최종 배포의 남은 검증에서는 5건을 다시 수집하지 않습니다.

```bash
uv run --locked python -m app.chat.deployment_check \
  --live \
  --base-url https://codyssey-b7-1-term-project-production.up.railway.app \
  --output app/chat/samples/ee-23-실행일.json
```

EE-19와 같은 질문을 독립된 새 대화에서 easy·beginner·advanced로 보냅니다.
advanced 대화에서는 현재 수준을 easy로 바꿔 “더 쉽게”, “예시 하나 더”를 보냅니다.
최대 5회의 신규 질문만 전송하고 자동 재시도를 하지 않습니다.
첫 완료 요청을 같은 키로 한 번 재전송해 같은 턴이 반환되는지 확인합니다.
API 관측만으로 AI 재호출 여부를 직접 증명하지 않으므로 운영 로그도 확인해야 합니다.

각 응답의 본문 `request_id`와 헤더 `X-Request-ID`를 함께 보존합니다.
새 요청은 둘이 같고, 완료 재전송은 본문에 최초 요청 ID가 남고 헤더에는 새 HTTP 요청 ID가 생깁니다.
저장된 상세 기록의 턴 ID·수준·질문·답변·상태도 응답과 비교합니다.

### 수동 품질 검토

실제 수집 후 원문을 고치지 않고, 수준 차이·주제 유지·현재 easy 적용·해요체·일반 텍스트·완결성을 검토했습니다.
API 정의의 비교 기준은 [MDN API 설명](https://developer.mozilla.org/en-US/docs/Glossary/API)입니다.
비유는 개념 이해용이고, 특정 서비스의 실제 동작을 검증한 것으로 보지 않습니다.

| 항목 | 관찰 결과 |
|---|---|
| 수준 차이 | easy는 식당·웨이터 비유, beginner는 요청→응답→화면의 흐름, advanced는 인터페이스 명세·추상화·API 종류 설명 |
| 후속 질문 | C의 두 후속 답변 모두 API 주제를 이어가며 쉬운 식당·로그인 예시 사용. 현재 easy 요청과 저장된 수준 일치 |
| 말투·완결성 | 5건 모두 해요체이며 문장상 잘림 없음 |
| 일반 텍스트 | 표·강조·코드펜스는 없으나 B-beginner와 C-easier에 `-` 목록이 있음. 번호 목록만 쓰도록 한 지침을 완전히 지킨 결과로 보지는 않음 |
| 비유 일관성 | C-easier는 첫 문장의 “주문서”에서 본문의 “메뉴판”으로 비유 대상이 바뀜. 개선이 필요한 관찰로 원문 보존 |
| 초보 용어 | B-beginner는 요청·응답 흐름을 보여 주지만 각각의 용어 정의를 따로 풀지는 않음. 수준 차이가 모든 항목에서 충분하다고 판정하지 않음 |
| 실제 서비스 예시 | C-example의 카카오 로그인은 개념 설명으로 단순화됨. 인증·동의·인가 코드·토큰·사용자 조회 등 실제 절차 전체의 검증 자료가 아님 |

[카카오 로그인 공식 절차](https://developers.kakao.com/docs/ko/kakaologin/rest-api#before-you-begin-process)는
인가 코드 요청, 토큰 요청, 서비스의 사용자 로그인 처리를 구분합니다.
모델 답변은 실제 구현 안내로 그대로 사용하지 않습니다.
프롬프트가 이미 요구하는 비유·형식 지침도 모델이 항상 지키는 것은 아니므로,
이번 5건을 근거로 모든 질문의 품질을 보장하지 않습니다. 답변 원문이나 기존 프롬프트는 수정하지 않았습니다.

## 시간 초과를 확인하는 절차

긴 질문이나 브라우저 연결 끊기로 서버 시간 초과를 단정하지 않습니다.
현재 공개 API에는 요청별 시간 제한을 바꾸는 기능이 없습니다.
팀장이 같은 코드의 별도 배포·별도 DB에 짧은 `AI_TIMEOUT_SECONDS`를 설정하는 방식이 권장됩니다.
운영 설정을 바꾸는 경우에는 점검 시간과 복구를 팀장이 관리해야 합니다.

재현 환경이 준비된 뒤에만 아래 명령을 실행합니다. 신규 질문은 한 건만 전송합니다.
예상과 달리 성공해도 추가 질문으로 시간 초과를 유도하지 않고 중단합니다.

```bash
uv run --locked python -m app.chat.deployment_check \
  --live --expect-timeout \
  --base-url https://팀장이-준비한-재현-환경 \
  --output app/chat/samples/ee-23-timeout-실행일.json
```

1. 실제 provider를 사용한 재현 환경에서 HTTP 클라이언트의 제한을 서버 제한보다 길게 둡니다.
2. `504 AI_TIMEOUT`, “응답이 지연되고 있어요. 잠시 후 다시 시도해 주세요.”를 확인합니다.
3. 상세 조회에서 `failed`, `error_code=AI_TIMEOUT`, `answer=null`을 확인합니다.
4. 같은 요청 키 재전송은 기존 실패를 반환하며 새 턴이 생기지 않는지 확인합니다.
5. `/health`가 계속 200인지 확인하고, 설정 복구 후 새 요청 키로 정상 응답을 확인합니다.

설정 복구는 팀장이 확인합니다. 복구 확인 뒤에는 5건 수집을 다시 돌리지 않고,
아래 명령으로 신규 질문 **한 건**의 정상 응답·저장·같은 키 재전송·health만 확인합니다.
실패한 요청의 키는 복구 확인에 재사용하지 않습니다.
여기서 요청 키는 중복 전송을 구분하는 `client_request_id`입니다. AI API 키를 새로 발급한다는 뜻은 아닙니다.

```bash
uv run --locked python -m app.chat.deployment_check \
  --live --check-recovery \
  --base-url https://팀장이-정상-설정으로-복구한-환경 \
  --output app/chat/samples/ee-23-recovery-실행일.json
```

시간 초과·복구 파일은 서로 다른 이름으로 보존합니다. 재현 환경의 커밋이 최종 배포 커밋과 같은지,
정상 제한값으로 복구됐는지도 위 운영 정보 표에 기록합니다.
클라이언트의 `ReadTimeout`만 발생하면 서버 결과는 **미확인**입니다.
실제 실패 턴·운영 로그를 확인하기 전까지 통과로 표시하지 않습니다.

## request_id로 서버 로그 확인

수집 파일에 기록한 최초 POST의 헤더 요청 ID로 Railway 로그를 검색합니다.
공개 기록에는 아래 이벤트의 ID·시각·상태·오류 코드만 옮깁니다.
로그 원본의 사용자 ID·이메일·쿠키·키·질문·답변은 넣지 않습니다.

```text
request_received
db_save_success status=pending
ai_call_start
ai_call_success 또는 ai_call_failed error_code=AI_TIMEOUT
db_save_success status=completed 또는 status=failed
request_completed status=200 또는 status=504
```

위는 기대 순서이며 실측 로그가 아닙니다. 운영 로그를 확보한 뒤 관측 결과를 별도로 추가합니다.
시간 초과 기록에는 재현 환경의 커밋·적용 제한값·확인 시각과 정상 설정 복구 결과도 남깁니다.

| 대상 | 최초 POST의 `X-Request-ID` | 확인 시각(KST) | 로그에서 확인한 흐름·HTTP 상태 | 근거 링크·기록 위치 |
|---|---|---|---|---|
| 최종 배포 기준 시간 초과 | 미확인 | 미확인 | 요청→AI 실패→failed 저장→504: 미확인 | 미확인 |
| 정상 설정 복구 후 새 요청 키 | 미확인 | 미확인 | 요청→AI 성공→completed 저장→200: 미확인 | 미확인 |

Railway의 별도 HTTP ID와 앱의 `X-Request-ID`를 혼동하지 않습니다.
재전송의 헤더 ID는 최초 요청과 다르므로, 최초 요청과 재전송을 구분해 검색합니다.
로그에서 같은 키 재전송에 `ai_call_start`가 추가되지 않는지도 함께 확인합니다.

## 키 한도와 횟수 제한 제안

현재 코드 기본값은 사용자 최근 60초 10회, 서비스 전체 UTC 하루 200회입니다.
서버의 요청 제한은 게이트웨이 키의 남은 예산과 다릅니다.
실패한 AI 시도도 횟수를 쓰며, 완료·실패 재전송은 새 AI 호출 횟수를 쓰지 않습니다.
이 제한은 단일 worker·단일 인스턴스 메모리에 있으며 재시작하면 초기화됩니다.
따라서 하루 200회를 키 사용량의 강제 상한으로 간주할 수 없습니다.

EE-19 최신 5건은 총 8,451토큰, 평균 약 1,690토큰이었습니다.
이는 소수 로컬 표본의 응답 메타데이터이며, 이번 배포의 사용량·청구 단위·최대 비용이 아닙니다.
대화 문맥이 길어지면 입력 사용량도 늘어납니다.

운영 키의 잔여량·한도 단위·초기화 시각·모델 가중치·다른 도구와 공유 여부를 확인한 뒤,
평가 시연용 예산을 남기고 보수적인 1회 사용량으로 나눠 일일 제한을 제안합니다.
자료 확인 전에는 기존 값을 임의로 올리거나 확정된 안전 예산으로 표현하지 않습니다.

| 운영자가 확인할 항목 | 값·근거 | 확인 시각(KST) |
|---|---|---|
| 운영 키 잔여량과 단위(토큰·크레딧 등) | 미확인 | 미확인 |
| 한도 초기화 시각·시간대 또는 만료 | 미확인 | 미확인 |
| 배포 모델 가중치와 잔여량에 적용되는 방식 | 미확인 | 미확인 |
| 다른 도구와 공유 여부·다른 작업에 남길 예산 | 미확인 | 미확인 |
| 보수적인 1회 소모량·산정 근거 | 미확인 | 미확인 |
| 평가 시연 예산과 추가 여유 예산 | 미확인 | 미확인 |

잔여량·예산·1회 소모량은 같은 단위로 맞춥니다. 관리자 화면의 단위가 모델 가중치를
이미 반영한다면 가중치를 다시 곱하지 않습니다. 자료는 키 문자열을 가린 기록으로 남깁니다.
`사용 가능한 예산 = 잔여량 - 다른 작업 예산 - 시연 예산 - 여유 예산`으로 계산하고,
`사용 가능한 예산 ÷ 보수적인 1회 소모량`의 소수점을 버린 횟수를 상한 후보로 삼습니다.
값이 0 이하라면 추가 AI 호출을 멈추고 운영자와 예산을 확인합니다.
초기화·만료 기간에 맞춰 남은 날짜도 고려하며, 현재 하루 200회보다 높이지 않는 방향으로 제안합니다.
사용자 60초 10회도 자동으로 올리지 않습니다. 실제 설정 변경은 팀장 확인 후 진행합니다.
메모리 제한이 재시작으로 초기화되는 특성까지 고려하므로, 계산한 횟수만으로 키 예산이 보장된다고 쓰지 않습니다.
