# EE-13: 질문을 받아 AI 답변을 저장하기

`POST /api/chat`을 EE-05 provider, EE-10 프롬프트·문맥, EE-11 DB 함수와 연결합니다.
API·DB 명세를 바꾸지 않고 `app/chat/`에서 처리 순서를 조립합니다.

## 설명할 핵심 세 가지

1. **AI보다 먼저 질문을 저장합니다.** 인증·CSRF·대화 소유권과 입력을 확인한 뒤
   `pending` 턴을 저장합니다. 성공하면 같은 턴을 `completed`, AI 실패면 `failed`로 바꿉니다.
2. **같은 요청 번호로 AI를 두 번 부르지 않습니다.** `client_request_id`는 한 번의 전송을
   구분하는 UUID입니다. 완료된 요청은 저장한 답변을 반환하고, 실패한 요청은 같은 오류를 반환합니다.
3. **AI를 기다리는 동안 DB 트랜잭션을 열어 두지 않습니다.** 필요한 문맥을 일반 자료로
   복사하고 읽기 트랜잭션을 `rollback()`으로 끝냅니다. 이미 `commit()`한 `pending`은 남습니다.
   답변을 받은 다음에 새 트랜잭션으로 결과를 저장합니다.

## 파일별 역할

| 파일 | 역할 |
|---|---|
| `schemas.py` | UUID·설명 수준·질문 1~2,000자 검증, 계약에 없는 필드 거부 |
| `router.py` | 공통 인증·CSRF·DB·설정·provider를 받아 서비스 호출 |
| `service.py` | 소유권 → 중복 확인 → pending 저장 → 문맥 → AI → 결과 저장 |
| `anthropic_provider.py` | Anthropic SDK 요청, 시간·출력 상한, SDK 오류 변환 |
| `provider.py` | 서버 설정에 따라 Fake 또는 Anthropic 선택 |

질문은 앞뒤 공백을 제거한 뒤 길이를 검사합니다. 요청 본문에서 사용자 ID를 받지 않습니다.
없는 대화와 다른 사람 대화는 모두 `404 CONVERSATION_NOT_FOUND`로 응답하며 AI를 호출하지 않습니다.

## 한 질문의 처리 순서

1. EE-11 함수로 로그인 사용자의 대화인지 확인합니다.
2. 같은 사용자의 `client_request_id`가 이미 저장됐는지 확인합니다.
3. 새 요청이면 사용자별 처리 중 표시를 하고, EE-11 함수로 `pending`을 저장합니다.
4. 같은 사용자·같은 대화의 **완료된 턴만** `HistoryTurn`으로 복사합니다.
5. EE-10 함수에 `context_turns`·`context_max_chars`와 **이번 요청의 수준**을 전달합니다.
6. 읽기 트랜잭션을 끝내고, 설정된 제한 시간 안에서 AI를 한 번 호출합니다.
7. 성공·실패를 EE-11 함수로 저장하고 공통 응답을 반환합니다. 처리 중 표시는 항상 해제합니다.

`context_turns` 또는 `context_max_chars`가 0이면 과거 문맥 없이 현재 질문만 보냅니다.
오래된 문맥을 제외할 때는 질문과 답변을 한 쌍으로 뺍니다.

## 중복 요청과 재시도

| 상황 | 결과 |
|---|---|
| 같은 키·같은 내용, 이미 완료 | 저장된 응답 반환, AI 추가 호출 없음 |
| 같은 키, 대화·질문·수준 중 하나가 다름 | `409 REQUEST_CONFLICT` |
| 같은 키가 아직 처리 중 | `409 CHAT_BUSY` |
| 같은 키가 실패함 | 저장된 오류 반환, AI 자동 재호출 없음 |
| 사용자가 실패 후 다시 시도하기로 결정 | 새 UUID로 새 요청 |
| 같은 사용자의 다른 새 질문이 처리 중 | `409 CHAT_BUSY` |

완료된 응답을 재전송할 때는 최초 결과의 `request_id`도 유지합니다.
사용자별 처리 중 표시는 **단일 서버 프로세스의 메모리**에서 관리합니다.
같은 키의 중복 저장은 DB 유일 제약도 막습니다. 여러 프로세스로 배포하려면 사용자별 잠금은 별도로 바꿔야 합니다.

PR #41 화면의 수준 값과 후속 문구(더 쉽게·예시 하나 더·핵심만)를 그대로 받습니다.
서버는 UTC 시각을 보내고 화면이 한국 시간으로 표시합니다. 응답을 받지 못해 처리 결과를 모를 때는
같은 UUID로 재전송해야 중복 호출을 피할 수 있습니다. 화면의 재시도 UUID 관리는 EE-14에서 함께 확인합니다.

## 실제 AI 설정과 오류

`AI_PROVIDER=anthropic`일 때 `anthropic_base_url`·`anthropic_api_key`·`ai_model`을 사용합니다.
키는 `.env`에만 두고 커밋하지 않습니다. `AI_PROVIDER=fake`는 키·외부 통신 없이 동작합니다.

- SDK `max_retries=0`: 비용이 중복 발생할 수 있는 자동 재시도를 끕니다.
- `ai_timeout_seconds`: SDK 제한과 서비스의 전체 대기 제한에 함께 사용합니다.
- `ai_max_output_tokens`: Messages API의 `max_tokens`로 전달합니다.
- 401·403·404·429 SDK 응답 → `AI_UNAVAILABLE`(503), 시간 초과 → `AI_TIMEOUT`(504).
- 그 밖의 SDK 오류·빈 답변 → `AI_UPSTREAM_ERROR`(502), DB 실패 → `DB_ERROR`(503).

취소된 요청도 가능한 경우 실패로 저장합니다. DB 자체가 실패하면 저장 결과가 불확실하거나
`pending`이 남을 수 있으므로 성공으로 응답하지 않고, AI를 자동 재호출하지도 않습니다.
질문·답변·키·SDK 오류 원문은 로그에 넣지 않습니다. 요청 ID로 AI 시작·성공·실패와 DB 이벤트를 연결합니다.

Fake·임시 SQLite로 성공/실패 저장, 인증·CSRF·소유권, 입력 경계, 문맥·수준 변경,
중복 요청·동시 요청·취소·DB 실패를 검사합니다. Anthropic 테스트는 설치된 SDK에
모의 HTTP 전송을 넣어 요청 형식과 예외 변환을 확인합니다. 실제 키·유료 AI 호출은 사용하지 않습니다.
