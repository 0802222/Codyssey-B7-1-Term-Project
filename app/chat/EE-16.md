# EE-16: AI 오류와 질문 횟수 제한

EE-13의 오류·중복 요청 처리를 다시 검수하고, AI 호출 직전에 횟수 제한을 추가했습니다.
API·DB 필드를 바꾸지 않고 `Settings`의 기존 두 설정을 사용합니다.
[EE-16 PR #44](https://github.com/easy-explain/Codyssey-B7-1-Term-Project/pull/44)는
선행 EE-13 PR #43이 `main`에 병합된 뒤 기준 브랜치를 `main`으로 바꾸어 최종 확인합니다.

## 설명할 핵심 세 가지

1. **AI를 부를 새 질문만 셉니다.** 입력·인증·소유권·중복 요청을 먼저 확인하고,
   질문 저장과 문맥 준비까지 성공한 다음 횟수를 셉니다. 준비 단계 DB 실패는 횟수를 쓰지 않습니다.
2. **두 한도를 한 번에 확인합니다.** 사용자별 최근 60초와 서비스 전체 하루 한도를
   같은 짧은 `Lock` 안에서 검사하고 함께 증가시킵니다. 두 사용자가 동시에 보내도 초과 허용하지 않습니다.
3. **횟수 제한이 AI 호출 재시도를 만들지 않습니다.** 초과하면 AI 없이 429를 반환하고
   이미 저장한 턴을 `failed / RATE_LIMITED`로 바꿉니다. 같은 키 재전송도 기존 429를 반환합니다.

## 파일과 처리 순서

- `rate_limit.py`: 앱이 공유하는 `ChatRateLimiter`와 FastAPI 의존성입니다.
- `router.py`: 인증·설정·DB·provider와 함께 `RateLimiterDep`를 서비스에 전달합니다.
- `service.py`: EE-13 처리 흐름의 AI 호출 직전에 한도를 확인하고, 429도 기존 실패처럼 저장합니다.

처리 순서:

`인증·입력 → 소유권 → 중복·처리 중 확인 → pending 저장 → 문맥 복사 → 읽기 트랜잭션 종료 → 횟수 확인·집계 → AI → 결과 저장`

한도 초과 시에도 pending을 그대로 두지 않습니다. 다만 DB 저장 자체가 실패하면 기존 명세대로
503 `DB_ERROR`이며, 성공으로 응답하거나 AI를 자동 호출하지 않습니다.

## 무엇을 몇 번 세나요?

| 설정 | 기준 | 기본값 |
|---|---|---|
| `USER_REQUESTS_PER_MINUTE` | 같은 사용자가 최근 60초에 시작한 AI 호출 | 10회 |
| `DAILY_REQUEST_LIMIT` | 모든 사용자가 UTC 하루 동안 시작한 AI 호출 | 200회 |

사용자 한도는 `monotonic()`으로 잰 최근 60초의 호출 시각을 `deque`에 보관합니다.
정확히 60초가 지난 기록부터 빼고, 기록이 없는 사용자도 지워 메모리가 계속 늘지 않게 합니다.
시스템 시계가 바뀌어도 60초 간격은 유지됩니다.

하루는 **UTC 00:00~다음 날 00:00**입니다. 한국 시간으로는 오전 9시에 일일 횟수가 초기화됩니다.
날짜가 바뀌어도 사용자별 최근 60초 기록은 유지하므로 자정을 걸친 연속 요청을 우회 허용하지 않습니다.

| 요청 결과 | 새 횟수 소모 |
|---|---|
| 실제 또는 Fake AI 호출 시작 | 1회 |
| AI 시간 초과·상위 오류·빈 응답·취소 | 이미 시작했으므로 1회 유지 |
| 완료/실패한 같은 요청 키의 재전송 | 없음 |
| 잘못된 입력·인증·CSRF·소유권·키 충돌·처리 중 거절 | 없음 |
| AI 준비 중 DB 실패 | 없음 |
| 한도 초과 429 | 없음. 두 한도 중 어느 쪽도 증가시키지 않음 |

실패를 다시 시도하기로 결정하면 **새 UUID**를 사용합니다. 기존 키는 시간이 지나 한도가 풀려도
저장된 실패를 반환합니다. 응답 유실로 결과를 모르는 상황은 같은 키를 써서 중복 AI 호출을 피합니다.

## 오류 응답과 로그

| 상황 | HTTP / code |
|---|---|
| `AITimeoutError` | 504 `AI_TIMEOUT` |
| `AIUpstreamError`·빈 응답 | 502 `AI_UPSTREAM_ERROR` |
| `AIUnavailableError` | 503 `AI_UNAVAILABLE` |
| 우리 서비스의 질문 한도 초과 | 429 `RATE_LIMITED` |
| 처리 중 / 같은 키에 다른 내용 | 409 `CHAT_BUSY` / `REQUEST_CONFLICT` |

429 안내는 “질문 요청 한도를 초과했어요. 잠시 후 다시 시도해 주세요.”입니다.
한도 초과는 `chat_rate_limited` 이벤트로 남기며 AI 시작 이벤트를 만들지 않습니다.
질문·답변·키·SDK 오류 원문은 오류 응답이나 로그에 넣지 않습니다.

## 운영 제한과 검증

횟수는 **서버 메모리**에만 있습니다. **worker 1개·인스턴스 1개에서만 정확하며, 재시작하면 초기화됩니다.**
여러 worker나 인스턴스로 늘리려면 카운터와 처리 중 잠금을 공유 저장소로 옮겨야 합니다.
이 한도는 AI 호출 횟수 제한이므로 제공자의 실제 요금·토큰 상한을 보장하지 않습니다.

```bash
uv run --locked ruff check .
uv run --locked pytest tests/chat
uv run --locked pytest
```

실제 키 없이 Fake와 임시 SQLite로 오류별 응답·실패 저장·중복 요청을 검사합니다.
시간 함수만 바꾼 테스트로 60초·UTC 날짜 경계, 사용자 격리·일일 합산·동시 집계를 확인합니다.
실제 유료 AI 호출과 생성 문장의 품질 검증은 이 작업에서 실행하지 않습니다.
